# P4.5 持久化与生产化实施计划

> 介于 [[docs/plans/phases/P4-git-collab|P4]]（已完成）与 [[docs/plans/phases/P5-advanced-rag|P5]]（待启动）之间的桥接阶段。把 Calliodesmo 从"内存易失单机演示"推到"持久化多用户生产可用"。
> **For agentic workers:** 按 Task 编号顺序执行（顺序由用户锁定，勿重排）；步骤用 checkbox（`- [ ]`）跟踪；每 Task 内 TDD（先写失败测试 -> 实现 -> 跑绿 -> 提交）。

## 目标与范围

把三层 stores 从内存易失升级为 Postgres+pgvector/Neo4j 真后端，增量索引消灭"每次新增全量重跑 ECL"的资源消耗，P4 协作推送完善为"合并真正落库、重启不丢"，前端可上传文档异步建图，实体对齐走 embedding 三段式 + 人工复核。

**与 roadmap P9 的边界**：增量索引 MVP 从 [[docs/plans/roadmap|roadmap]] P9「动态更新与规模化」剥离到本阶段；roadmap P9 仍保留 Qdrant/Milvus 置换、Celery+Redis、审计硬化/合规/多租户压测、社区规模化增量。本阶段 ≠ P9。

**范围外（留 roadmap P9 / 后续）**：Celery+Redis 异步批处理；Qdrant/Milvus 置换 VectorStore；ES 替换 BM25；社区真增量算法；审计硬化查询 UI；多租户压测。

## 顺序总览（用户锁定）

| # | Task | 承诺 | 说明 |
|---|---|---|---|
| 1 | 清 SQLite，走 `.env` 连真实 PG+Neo4j | ✅ 批次 | 破坏性，单独 PR |
| 2 | 三 store 真后端持久化 | ✅ 批次 | pgvector / Neo4j / Postgres |
| 3 | 增量索引 | ✅ 批次 | 消灭全量重跑 ECL |
| 4 | P4 功能完善 | ✅ 批次 | 合并落库贯通 + 双写一致性 |
| 5 | 前端 ingest UI + 异步 job | 🔁 持续 | Task 4 闭合后接续 |
| 6 | embedding 三段式 + 人工复核 UI | 🔁 持续 | Task 4 闭合后接续 |

**Task 1-4 为承诺批次**（闭合即 P4 生产可用 + 持久化 + 增量）。**Task 5-6 步骤已写全**，Task 4 闭合后直接按步骤启动，无需重新规划。

**为什么是这个顺序**
- **先持久化（1+2）**：内存态下验证 P4 只能证明同进程逻辑对，无法证明"合并进后端数据库"。持久化是后续一切的生产基线。
- **增量紧跟（3）**：复用 `graph_merge` **纯函数**（操作 dataclass、不碰 DB，持久化无关），与 P4 跨 scope 推送是不同调用路径，**不依赖 Task 4**；提前做让 Task 4 与后续每次 ingest 都省算力。
- **P4 完善收尾（4）**：在持久化 + 增量基线上做全量回归 + 合并落库贯通 + 双写一致性修复。
- **摄入 UI（5）→ 三段式（6）**：Task 5 补齐 P3 缺失的摄入 UX（基础），Task 6 提升 P4 合并的实体对齐质量（高级）。二者相对独立。

## Task 3: 增量索引

**目标：** 文档新增/更新/删除只重算受影响子图，不残留脏数据，不重复抽取。复用 Task 2 `documents` 表（content_hash）+ P4 `graph_merge` 纯函数。

> [!important] 核心动机
> 当前 `ECLIndexingEngine.ingest()`（`ecl/engine.py:57-112`）每次都对输入批次从头跑 Extract→Cognify→Load，**不读历史、不跳过未变文档**——LLM 调用随库增长线性累积（100 篇库加 1 篇，可能重算远超 1 篇）。增量消灭这笔重复：指纹判定"哪些真变了"，未变短路、变更只重算受影响子图。**硬指标**：① 二次 ingest `call_count==0`；② 新增 1 篇到 N 篇库 `call_count` 仅 = 1 篇量（不随 N 涨）；③ 更新后旧 chunk/孤儿实体清除、共享实体保留；④ 成员不变的社区 id 稳定、手改社区不被覆盖。

> [!important] 前置门禁（非全量 P4 回归）
> 增量复用 `graph_merge` **纯函数**（不碰 DB，持久化无关）。**Step 3 前**跑：
> ```bash
> uv run pytest tests/test_graph_merge.py tests/test_merge_service.py -v
> ```
> 全绿即可。完整 P4 贯通验证归 Task 4，不阻塞本 Task。

**Files:** `interfaces/document_loader.py:10-13`（`content_hash`）· `providers/_base_loader.py:43-60`（sha256）· `interfaces/{vector,graph,community}_store.py`（加 `delete_by_doc`/`remove_orphans`）· 三 store 真后端跟进 delete· `ecl/engine.py:57-112`（增量分支）· `collab/graph_merge.py`（抽 `prune_source_chunks` 反向纯函数）· `ecl/cognify.py:263,308` + `doc_community_clusterer.py:57`（id 稳定化）· `api/ingest.py`（`DELETE /ingest/{doc_id}`）· `config.py`（`incremental_indexing`）· Test `tests/test_incremental_indexing.py`。

## 依赖与风险

- **不可逆清 SQLite（Task 1）**：旧 `data/*.db` 作废；本地强依赖 `.env` 连真实 PG+Neo4j（**不用 docker**）。缓解：单独 PR+合入前全量；`sys.modules` 桩仅删 SQLite 部分；StubLLM 不依赖外部 key；CI `@pytest.mark.db` 跳过，全量回归靠本地——纪律上每次提交前本地无 `-m` 全量过。
- **pgvector 维度对齐（Task 2）**：列维度须与 `embedding_dimension` 一致。缓解：维度进 config，建表前断言；hash 模式小维度。
- **Neo4j+PG 双写一致性（Task 2.3/Task 4.4）**：两轨写非原子。缓解：Task 4 两阶段提交或读以 Neo4j 为准；CommunityVersion 快照兜底。
- **增量 delete 误删（Task 3.2）**：`remove_orphans` 误删共享实体。缓解：`prune_source_chunks` 按 `source_chunk_ids` 成员判定，空集才删；测试"共享实体保留"。
- **增量与 P4 合并耦合（Task 3 vs 4）**：Task 4 若改纯函数签名，Task 3 调用点同步。缓解：Task 3 门禁；Task 4 优先改 service 层不动纯函数签名。
- **异步 worker 丢 job（Task 5）**：serve 重启丢 running job。缓解：job 表记 status，启动扫 running→failed；Celery+Redis 留 roadmap P9。
- **三段式阈值经验值（Task 6）**：hash 嵌入区分度弱。缓解：阈值进 config 可调；BGE-M3 模式；评估 harness 接对齐质量回归。
